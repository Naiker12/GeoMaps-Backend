============================================================
1. RESUMEN EJECUTIVO
============================================================

El sistema ya tiene una base funcional para administrar capas GIS:

- El backend guarda capas en la tabla layers y geometria individual en layer_features.
- Cada capa tiene name, description, category, subcategory, source, visibility, map_color, map_opacity, file_url, stats_config, feature_card_config y symbology.
- La categoria y subcategoria no son tablas independientes. Hoy son campos de texto dentro de cada capa.
- El admin ya permite crear una capa nueva y escribir/seleccionar categoria usando un Combobox.
- El mapa publico agrupa automaticamente las capas por category en LayerContext.
- El panel de capas ya muestra categorias colapsables, activa/desactiva capas, permite descargar recursos y abrir tabla de datos.
- El chat IA puede activar capas, filtrar capas, mostrar marcadores, hacer zoom, animar rutas y resaltar zonas usando map_actions.
- El selector de mapa base ya existe dentro del panel lateral de capas, pero no como cuadro pequeno flotante encima del mapa.

La mejora que se quiere agregar encaja bien con la arquitectura actual, pero conviene ordenar tres frentes:

1. Admin: mejorar el flujo de crear capa con categoria nueva o categoria existente, y manejar mejor subcategoria.
2. Mapa: agregar un selector pequeno de mapas base flotante sobre el mapa, sin depender de abrir el panel de capas.
3. Panel de capas: agregar filtros tipo select/combobox por categoria y subcategoria, para navegar capas con muchas categorias.

2. BACKEND ACTUAL DE CAPAS
============================================================

Archivos principales:

- app/db/models/layer.py
- app/schemas/layer.py
- app/api/v1/layers.py
- app/services/layer_service.py
- app/repositories/layer_repository.py

Modelo actual:

Tabla layers:

- id: UUID
- name: nombre de la capa
- description: descripcion
- category: categoria textual
- subcategory: subcategoria textual
- source: fuente de datos
- geometry_type: tipo geometrico detectado
- source_type: actualmente se guarda como FILE
- visibility: PRIVATE, TEAM o PUBLIC
- map_color: color base de mapa
- map_opacity: opacidad
- file_url: archivo original subido a storage
- stats_config: configuracion JSONB para estadisticas
- feature_card_config: configuracion JSONB para ficha de feature
- symbology: configuracion JSONB de simbologia
- created_by
- created_at / updated_at

Tabla layer_features:

- id: BigInteger
- layer_id: referencia a layers
- display_name: nombre canonico generado por normalizador
- properties: JSONB con atributos originales
- geom: Geometry SRID 4326
- created_at

Endpoints actuales:

- POST /api/v1/layers/
  Crea una capa con archivo .geojson, .json o .zip.
  Requiere usuario autenticado.

- GET /api/v1/layers/categories
  Devuelve categorias unicas tomadas desde layers.category.

- GET /api/v1/layers/
  Lista capas. Si no hay usuario autenticado, fuerza visibility=PUBLIC.

- PATCH /api/v1/layers/{layer_id}
  Actualiza metadatos, archivo y/o simbologia.

- GET /api/v1/layers/{layer_id}/features
  Devuelve GeoJSON FeatureCollection de la capa.

- GET /api/v1/layers/features/properties
  Devuelve propiedades combinadas de varias capas.

- GET /api/v1/layers/features/{feature_id}
  Detalle de una feature.

- GET /api/v1/layers/{layer_id}/field-values
  Valores unicos de un campo para simbologia categorizada.

- GET /api/v1/layers/{layer_id}/field-stats
  Estadisticas numericas para simbologia graduada.

- DELETE /api/v1/layers/{layer_id}
  Elimina capa, features y archivo del storage.

Observaciones importantes:

- No existe tabla categories ni layer_categories.
- Crear una categoria nueva no requiere endpoint especial: basta con enviar category="Nueva Categoria" al crear o editar una capa.
- La subcategoria funciona igual: es texto libre en layers.subcategory.
- El endpoint /layers/categories solo devuelve categorias, no subcategorias.
- Si se quiere filtrar por categoria desde backend, hoy habria que agregar query params porque list_layers solo filtra por visibility.
- El repositorio tiene get_unique_categories(), pero no get_unique_subcategories() ni estructura categoria -> subcategorias.

Riesgo detectado:

- En app/repositories/layer_repository.py se usa delete(...) en delete_features_by_layer_id, pero en los imports visibles no aparece delete importado desde sqlalchemy. Si ese metodo se ejecuta al reemplazar archivo de una capa, puede fallar. Conviene revisar/corregir.

Flujo actual para agregar capa:

1. Admin entra a la pagina Capas.
2. CapasPage carga layersService.getLayers().
3. La tabla muestra las capas existentes.
4. Boton "Agregar Capa" abre CapasModal.
5. CapasModal renderiza CapasForm.
6. CapasForm carga categorias con layersService.getCategories().
7. El campo Categoria es Combobox:
   - Permite seleccionar una categoria existente.
   - Permite escribir una categoria nueva.
   - Si el texto escrito no existe, muestra "Nueva: {valor}".
8. El admin llena:
   - Nombre
   - Categoria
   - Visibilidad
   - Subcategoria opcional
   - Fuente
   - Color
   - Opacidad
   - Descripcion
   - Archivo .zip o .geojson
9. Al guardar, CapasPage llama:
   - layersService.createLayer(data, files) si es nueva.
   - layersService.updateLayer(id, data, files) si edita.
10. Layer-Service arma FormData con category y subcategory como texto.
11. Backend procesa archivo, crea metadata en layers e inserta features en layer_features.
12. Admin refresca tabla con fetchCapas().

Conclusion:

El flujo de "crear categoria nueva al crear capa" ya esta parcialmente resuelto. No hay que crear primero una categoria. La categoria nace cuando una capa se guarda con ese texto.

Lo que falta para que el flujo se sienta completo:

- Mostrar categoria y subcategoria en la tabla de admin.
- Agregar filtro por categoria en la tabla de admin.
- Agregar filtro por subcategoria si aplica.
- Normalizar el texto antes de guardar, por ejemplo trim y evitar categorias vacias con espacios.
- Mejorar el campo subcategoria para que tambien pueda seleccionar existentes segun categoria.
- Refrescar categories despues de crear/editar para que la nueva categoria aparezca sin recargar pagina.

4. PROPUESTA: FLUJO ADMIN PARA CATEGORIA NUEVA O EXISTENTE
============================================================

Flujo recomendado para Nueva Capa:

1. Admin hace click en "Agregar Capa".
2. Se abre dialog/modal "Nueva Capa de Informacion".
3. Campo Categoria:
   - Tipo: Combobox.
   - Opciones: categorias existentes desde /layers/categories.
   - Permite escribir texto.
   - Si escribe algo nuevo, mostrar "Crear categoria: X".
4. Campo Subcategoria:
   - Tipo recomendado: Combobox editable.
   - Si ya se selecciono categoria, mostrar subcategorias existentes de esa categoria.
   - Si no hay categoria, permitir escribir texto pero indicar que depende de la categoria.
5. Admin carga archivo .zip o .geojson.
6. Admin define visibilidad:
   - PRIVATE: solo admin/autenticados.
   - TEAM: equipo.
   - PUBLIC: disponible para mapa publico.
7. Admin define estilo inicial:
   - Color
   - Opacidad
8. Al enviar:
   - Frontend manda category y subcategory en FormData.
   - Backend crea capa.
   - Si category no existia, queda creada implicitamente porque existe una capa con esa category.
9. Al terminar:
   - Refrescar lista de capas.
   - Refrescar lista de categorias.
   - Mostrar toast claro: "Capa creada en categoria X".

Flujo recomendado para capa en categoria existente:

1. Admin abre "Agregar Capa".
2. Selecciona una categoria ya existente del Combobox.
3. Selecciona o escribe subcategoria.
4. Guarda.
5. La nueva capa aparece agrupada dentro de esa categoria en el mapa.

Flujo recomendado para editar categoria/subcategoria de una capa:

1. Admin abre menu de capa -> Editar Metadatos.
2. Se abre el mismo formulario con initialData.
3. Puede cambiar categoria y subcategoria.
4. Al guardar, PATCH /layers/{id} actualiza los textos.
5. En el mapa, cuando se refresque LayerContext, la capa cambia de grupo.

Validaciones recomendadas:

- category requerido en frontend y backend.
- category.trim().length >= 1.
- subcategory opcional, pero si se envia debe trim().
- Limitar longitud segun backend: category max 100, subcategory max 120.
- Evitar duplicados visuales por espacios/capitalizacion:
  "Movilidad", " movilidad " y "MOVILIDAD" deberian tratarse con criterio.

Opcion simple:

- Guardar exactamente el label que escriba el usuario, pero trim.

Opcion mas robusta:

- Crear tabla categories con id, name, slug, parent_id.
- Migrar layers.category y layers.subcategory a category_id/subcategory_id.
- Esto da mas control, pero es mas trabajo.

Recomendacion para esta etapa:

Mantener category/subcategory como texto y mejorar UI + filtros. No meter tabla nueva todavia, salvo que se necesiten permisos, orden manual, iconos, descripcion o portada por categoria.

13. DECISION CLAVE: CATEGORIAS COMO TEXTO VS TABLA
============================================================

Mantener como texto conviene si:

- Solo se necesita agrupar capas.
- No se requiere ordenar categorias manualmente.
- No se requieren iconos, permisos o descripcion por categoria.
- El admin puede escribir categoria libremente.

Crear tabla de categorias conviene si:

- Se necesitan categorias administrables sin capas.
- Se quieren iconos/colores por categoria.
- Se necesita orden personalizado.
- Se necesitan permisos por categoria.
- Se quiere evitar duplicados de forma estricta.
- Se requiere jerarquia real: categoria -> subcategoria -> capa.

Recomendacion actual:

Por el estado del proyecto, mantener texto y mejorar flujo. Es mas rapido, menos riesgoso y ya esta alineado con el backend y frontend existentes.
